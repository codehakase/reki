# Capture hook benchmarks

This directory measures the cost and reliability of invoking `reki capture`
from a Zsh prompt. It answers two practical questions:

1. How much prompt-visible latency does synchronous capture add compared with
   dispatching capture in the background?
2. When ten shells capture concurrently, does every attempted row reach the
   shared SQLite database?

The scripts are development tooling. They are not installed, embedded in the
binary, or intended to be sourced from a user's shell configuration. The
production hook is generated by `internal/shell/zsh.go`; these smaller fixtures
keep the measurement focused on process startup and database capture.

All commands use the fixed text `bench-capture`, and all data, configuration,
shell files, and logs are isolated in a temporary directory. The harness never
reads real shell history or the user's normal Reki database.

## Run

```zsh
zsh bench/run.zsh 1000 fg      # warm N + 20-cycle cold probe, foreground
zsh bench/run.zsh 1000 bg      # same, background/disowned
zsh bench/run.zsh 1000 both    # both variants, plus the 10-shell concurrency run
```

`REKI_BIN=/path/to/reki` overrides the binary under test. `REKI_KEEP=1`
keeps the mktemp tree for inspection. Setup or probe failures exit nonzero.

## Variants

* `hook_fg.zsh` — precmd calls `reki capture` synchronously. Measures the
  full prompt-visible cost: spawn + DB write + close.
* `hook_bg.zsh` — precmd dispatches with `&!`, stdout to `/dev/null`, stderr
  attached so capture can emit its one warning for the shell session. Measures
  dispatch cost; the database write continues in the background.

Both hooks: `$?` saved first and restored last, nounset-safe, zero stdout,
JSON payload on stdin with fixed benign text (`bench-capture`), and a
per-worker session ID composed from the shell PID and random values.

The current concurrency probe runs 10 workers with 30 captures each and
reports attempted and inserted row counts; they must match.

## Acceptance criteria

The capture design is acceptable when:

* prompt-visible p99 latency is below 10 ms, with a p50 goal below 5 ms;
* measurements pass on both Linux and macOS;
* warm, fresh-process, and ten-shell concurrent runs are measured; and
* every concurrency attempt is inserted into SQLite.

Background, disowned capture is the current implementation. The foreground
variant remains as a counterfactual and may replace it only if foreground
capture meets both latency thresholds on both operating systems without losing
rows.

## Historical results (macOS arm64, zsh 5.9, 2026-10-29)

These numbers predate the required 5000 ms `busy_timeout` restoration and the
production hook installation. They are retained as background data, not as a
passing benchmark gate. Re-run the current hook on macOS and Linux before
relying on these results for a release decision.

`bin/reki` built from this tree; `reki capture` real (redaction, insert, FTS).

Warm N=1000 per variant; cold = 20 fresh `zsh -f` processes per variant
(page-cache effects approximate; no `sudo purge`):

| variant | N    | p50 (ms) | p95 (ms) | p99 (ms) |
| :------ | :--- | -------: | -------: | -------: |
| fg      | 1000 | 10.191   | 12.008   | 14.130   |
| cold\*fg  | 20   | 2.300    | 2.919    | 3.482    |
| bg      | 1000 | 1.803    | 3.428    | 4.872    |
| cold\*bg  | 20   | 0.724    | 0.908    | 0.926   |

Concurrency, 10 parallel `zsh -f` workers x ~5 s sharing one data dir
(per-worker p99, ms):

* fg: 7.0 6.7 6.7 7.3 7.1 7.2 6.4 7.0 6.8 6.5
* bg: 12.9 14.8 13.6 14.1 13.2 13.2 15.3 14.3 14.2 13.8
* rows reported in DB: 2000. The old harness did not record attempted writes,
  so this result cannot demonstrate that no rows were lost.

Historical takeaway: foreground warm latency missed the budget while
background warm latency fit it. The current implementation remains
background and disowned, but current macOS and Linux measurements—including
attempted-versus-inserted row counts—are still required.
